Design mock-up — Remotes, revision 3 — approved by the maintainer on 2026-11-19, with the recommendations below. Push from the library to a chosen registry: one item or several, from the item (Push to…) or from the place (Push here…). Revision 2, browse and pull, was approved on 2026-11-16; everything it shows works on this page as it did. Today’s Image › Push… keeps its rules and its words: the dry run, the guard, the accounts, the tag rules and Cancel. What changes is how the destination is chosen and where a push starts. Sample data only: registry.lan.example and nas.example:5000 stand for private registries on the local network; digests and sizes are illustrative. Nothing connects to a registry or writes a file.

New in revision 3

  • Push to… on a library item, with the destination preselected by the Remotes rule and chosen in a Remotes-style chooser: registry, namespace, repository, tag. The verdict is on screen before anything is sent.
  • Push here… on a registry or namespace node (context menu, Image menu, toolbar) and in the node’s details pane: the place is fixed and the library items are picked.
  • Several items go one after another under one progress bar. Each has its own verdict; a refused one is skipped with its reason.
  • After a push the Remotes list shows the tag and the item’s Source names the registry, without a refresh. The local tag stays: pushing never renames.
  • The review block is under the window: what is drawn, the questions with a recommendation each, and the new glyphs and icons.

What is drawn

  1. Where a push starts. For library items, in Images, Installation media and Firmware alike: Image › Push to…, the toolbar’s Push… and the Push to… button of the item’s details pane. For a place: Image › Push here…, the toolbar’s Push… while a Remotes node is selected, the context menu of a registry or namespace node (right-click, the Menu key or Shift+F10) and the Push here… button of the node’s pane. A node’s pane shows while no tag is selected; a namespace now has one of its own.
  2. Push to…, one item. The item and its local tag, the Destination as text, and under it the chooser: the registries and namespaces of Tools › Preferences › Registries drawn as the Remotes tree draws them, then Repository and Tag. The text and the chooser show the same destination; changing one changes the other. Below: the dry run and the checks of today’s Push…, and the verdict. All of it is worked out from the image, the registry list and this session’s listing, so nothing is sent before Push.
  3. The Remotes rule preselects. A local tag that names a registry goes to that registry, under its own path and tag. A short tag pulled from the default registry goes back to registry.unemu.dev/unemu/. A short tag made here goes where it was pushed last; before its first push nothing is preselected and Push waits for a choice. Every preselection can be changed; the local tag stays whatever is chosen.
  4. Verdicts. Ready to push. Push refused by the guard, with today’s sentence and no override (user-supplied content towards unemu/, a namespace not marked private, a registry or namespace not in the list). Log in first: a private namespace needs a login before a push, as it does before a listing or a pull, and Log in… sits beside the failed check, as in the approved registry accounts mock-up. A version tag, or a revision tag of a set or package, that the registry has for another image: refused, with the next free tag suggested. A tag that is not a version and names another image: allowed, after today’s Move the tag to this image? with both digests. The same image under the same tag: nothing to upload.
  5. “As listed”. What the registry already has under the chosen name comes from the listing this session holds, so the checks cost no request. A registry not listed in this session says so, and the tag is read when the push starts, before any blob goes up, as today.
  6. Push here… The place is the node: a namespace, or a registry (its only namespace, or the whole registry for a whole-registry entry). The dialog lists the library with a verdict for this place per item; Ctrl (⌘ on macOS) or Shift selects several. Items that cannot go here are hidden behind a check box and say why. Each item goes under its own path and tag.
  7. Several items. One list, one progress bar. A tag that names a registry goes there; the short and local ones go to the registry and namespace picked once in the dialog, each under its own path and tag. Each row has its destination, its verdict and its checks. Skipped with the reason: refused by the guard, a tag that cannot move, a tag that would move (push it alone to confirm), already there, not logged in.
  8. Progress and Cancel. One item: today’s blob list, with the manifest and the tag written last. Several: one bar, a row per item (Waiting, Pushing, Pushed ✓, Skipped, Failed ✗, Cancelled, Not started). Cancel stops at the next blob or chunk; items already pushed stay pushed. A failure on the way marks its row and the next item starts.
  9. After a push. The Remotes list gains the repository or the tag from the manifest just pushed, with no request, and the tree’s counts follow. A tag pushed from a local tag of another name reads Pushed from here · as …. In the library the item’s Source reads local → registry.lan.example, and its pane lists each registry reference it was pushed to. A registry not listed in this session shows the tag when it is first listed.
  10. Pushing never renames. The local tag is the same before and after, whatever the destination. The dialog says so before the push and again after it. Pull… on the pushed row still adds the registry’s full name beside it, without fetching.
  11. Unchanged. Everything else on this page is revision 2 of the Remotes mock-up, whose notes stay in remotes.html: the tree, the list, the states, Pull…, Contents…. Machines are still never pushed.

Kept from today’s Push…, word for word where the build has the words

  • The dry-run table (Part, Type, Digest, Size, Redistribution, Recorded in), the check lines with ✓, ✗ and •, “Push refused.” with “There is no override for this rule.”, “Ready to push.”, the tag notes (version tag, revision tag, release alias, not a version), Move the tag to this image?, the blob statuses, “Manifest and tag — written after every blob”, and the outcome sentences.
  • Not in the build and not drawn: the Pause button of the registry accounts mock-up. Cancel keeps the accepted chunks, and the next push resumes them.

Asked, and decided by the maintainer with the recommendation (2026-11-19); the context menu follows the open library context-menu work (upc-5pw.82)

  1. What is preselected for a short tag made here? Drawn: where it was pushed last, else nothing, and Push waits for a choice. Today’s Push… fills in the local tag, which resolves to registry.unemu.dev/unemu/. Recommendation: as drawn. A private test image should never stand one Enter away from the public namespace, even though the guard would refuse most of them.
  2. What does Source say after a push? Drawn: the origin stays and the registry follows it, local → registry.lan.example (several: local → 2 registries), with the full references in the details pane. A tag made here that names a registry shows its whole name in the Name cell, since Source says local. Alternatives: Source turns into the registry’s host, which hides that the tag was made here and cannot name two registries; or a separate “Pushed to” column. Recommendation: as drawn. The store then records each push on the local tag, as it records where a pull came from.
  3. What does the Remotes row say for a tag pushed from a local tag of another name? Revision 2 would say Not pulled · same image as …, which reads wrong a moment after pushing it. Drawn: a new Local state, Pushed from here · as <local tag>, with Show in library; Pull… still adds the full name without fetching. Recommendation: the new state.
  4. A context menu on Remotes nodes? The desktop has no context menu yet. Drawn: one on registry and namespace nodes only, with Push here…, Refresh, Log in… and Registries…; every item is also in a menu or in the node’s pane. Recommendation: yes, for these nodes only. Library rows get theirs when all their commands are decided together.
  5. One dialog or two? Drawn: Image › Push… becomes Push to… and opens this dialog for the selection. The Image combo box goes (the selection is the image) and the one-click destination buttons give way to the chooser; the Destination text stays for pasting a reference. Recommendation: one dialog.
  6. May the checks use this session’s listing? Drawn: yes, marked “As listed”, with no request; the push’s own read of the tag stays the authority, and a tag that changed in between is caught there as today. Alternative: read the tag from the registry when the dialog opens, one request per item. Recommendation: the listing only.
  7. What may a batch do without asking? Drawn: nothing that needs an answer. An item whose tag would move is skipped with “push it alone to confirm the move”; one that is already there is skipped. Recommendation: as drawn, as Pull… skips a tag whose local name holds another image.
  8. A failure on the way: stop, or go on? Drawn: the row says Failed ✗ with the reason and the next item starts; the end line counts pushed, skipped and failed. Recommendation: go on, as Pull… of several tags does.
  9. Which repository name under a namespace? Drawn: the whole local path, without repeating the namespace: private/test/dos5-bench stays that under private/, and open-at-test becomes private/open-at-test. Today’s suggestion keeps only the last component (private/dos5-bench). Recommendation: the whole path, so a pull on another computer gives the same name back.
  10. A Push… button on the toolbar? Drawn beside Pull…: Push to… for selected library items, Push here… for a selected Remotes node. Recommendation: yes. It needs the Push icon, which the library mock-up drew and the desktop never painted.

Out of scope

  • Pushing machines, deleting tags on a registry, and copying from one registry to another without the library.
  • Drag and drop of library items onto a Remotes node.
  • Marking content open, source archives and vendor terms: the guard’s refusals for them read as today and are not redrawn.

New glyphs and icons — for the icon inventory.

New icon: Push, on the toolbar’s Push…. It is the Push icon of the library mock-up’s toolbar, which the inventory lists as not drawn; Pull’s arrow turned upwards.

New character in a mock-up: • U+2022, the mark of a check line that is a note. The build’s Push… already writes it.

Characters other mock-ups have, new to the Remotes pages: ✗ U+2717, a failed check and “Failed ✗” (registry accounts, get templates).

Characters of the Remotes mock-up, used in new places: → U+2192 in the Source cell after a push and before each destination; ✓ U+2713 in a passed check, “Pushed ✓”, “Uploaded ✓” and “Written ✓”; ⚠ U+26A0 before “Names another image now”.

Unchanged from the Remotes mock-up: the icons (application monitor, Start, Pull, Refresh, registry, namespace, lock, machine, image, media set, firmware, machine file, the four message pictures) and the characters · × – — ’ “ ” … › − ⌘ □ ▲ ▼. The registry, namespace and lock icons are drawn again in the destination chooser, in the Push here… heading and in the context menu’s node.
